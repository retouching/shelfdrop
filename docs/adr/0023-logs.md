# 0023. Logs read from the page
Status: Accepted
Date: 2026-10-24

## Context
Decided by the owner: the logs can be read from the site, without a shell on the machine. The API and the placement worker are two containers of one image; both write their records to stderr (JSON or text, `SHELFDROP_LOG_FORMAT`), which Docker keeps, but no container reaches the logs of another through Docker. Both already mount the volume `data` (the API on `/data/shelfdrop`, the worker on `/var/lib/shelfdrop`, [ADR 0016](0016-placement.md)), and both run as the uid 10001.

## Decision
- **The files** (`shelfdrop/logging/setup.py`): the API (`create_app()`) and the placement worker (`shelfdrop placement run`) write every record to stderr as before and to a file of the data directory, `logs/api.jsonl` and `logs/placement.jsonl` (`log_file`, `Settings.log_dir`), always one JSON object per line (`JsonFormatter`), whatever the format of stderr. The file is a `RotatingFileHandler` of 5 MiB that keeps two copies (`api.jsonl.1`, `api.jsonl.2`): 15 MiB at most per process, nothing to configure. The commands of the database (`shelfdrop db upgrade`, `check`) write no file. The file holds the records of stderr, so their rules: never an address, a header, a body, a query string or a secret.
- **The reader** (`shelfdrop/logs/`, `LogReader`): the API reads both files from the data volume they share. A read goes from the end of the file, by blocks of 64 KiB, the newest record first, into the rotated copies only while the page asks for more; a copy whose first record is newer than the page asked is opened but not read. Every file is opened before the first is read, and a file met twice (a rotation between two openings) is read once. A line that is not a record (a line cut while it is written) is skipped.
- **The route** `GET /api/v1/logs` ([API](../api.md#get-apiv1logs)): the session alone (`require_session`), never an access token: a record names works, accounts, files. Filters: the service (`api`, `placement`), the lowest level, a text searched without case in the message, the logger, the request id and the other fields; `limit` (200, at most 1000). The cursor of the older entries, `next`, is the timestamp of the last entry and its place among the entries of that millisecond, so that a page never cuts or repeats the entries of one millisecond while new ones are written.
- **Its reads stay out of the logs**: the page reads them again every few seconds; `AccessLogMiddleware` logs the success of `GET /api/v1/logs` at `DEBUG`, as `/health`.
- **The page**: the tab Journaux of Paramètres (`/parametres/journaux`, `web/src/components/settings/LogsTab.tsx`): the service, the lowest level, the text, Actualiser and the real time (every 2, 5, 10 or 30 seconds, `RefreshBar`), the older entries by Plus anciennes (which stops the real time), the other fields of an entry on demand.

## Rejected alternatives
- Reading the logs of Docker (`docker logs`) from the API: it needs the socket of Docker in the container, the control of every container of the machine.
- A table of the database: every record would be a write in SQLite, shared by both processes, for data that only needs to be read back for a while.
- A cursor by the offset in a file: a rotation renames the files and moves every offset.
- Settings for the size and the number of copies: 15 MiB per process are a few days of records at `INFO`; nothing asked for more.

## Consequences
- The volume `data` holds up to 30 MiB of logs more.
- A record older than the third file is gone from the page; the logs of Docker keep their own history.
- Records of the same millisecond written out of order by two threads may come once more or once less across two pages.
